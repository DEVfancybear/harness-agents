# Đặc tả triển khai P5 — giao việc, task DAG và workspace cô lập

[English](P5.en.md) | Tiếng Việt

Trạng thái: **đặc tả triển khai đang hiệu lực**. SPEC này chỉ cấp quyền cho
P5-S01 đến P5-S07. Nó không cấp quyền cho P6 external plugins, P7
delete/backup/release hay P8 Web UI, và không cấp quyền spawn implementation
agent, commit, push hay publish. Assignment P5 do prompt của user giao trực tiếp;
không có vòng phê duyệt riêng sau khi file SPEC này được viết, nên evidence cuối
phải ghi rõ giới hạn tương quan đó.

## 1. Prerequisite và source boundary

Checkout khởi đầu sạch tại `57f6ea7fa6030133007cebcb051ec1eda1af697a`
(`origin/master`). Evidence và handoff P4 được viết trước khi gauntlet cuối của P4
hoàn tất, nên vẫn ghi `partial`/`pending`. Vì vậy P5 xác minh lại gate tiền nhiệm
từ source thay vì tin hai tài liệu đó.

Hai lần chạy thật `pwsh -NoProfile -File scripts/Verify-Phase.ps1 -Phase P4 -Json`
đã được thực hiện. Lần đầu fail trong bước `workspace-tests` vì lỗi môi trường:
`p3_c23_project_identity_requires_explicit_reassociation` không chạy được
`git clone` do `sh.exe` của Git báo
`fatal error - couldn't create signal pipe, Win32 error 5`. Một probe tối thiểu
(`git init` + `git clone` repository một file trong `$env:TEMP`) tái hiện đúng lỗi
đó, chứng minh nguyên nhân là giới hạn pipe của shell trong sandbox, không phải
source P4. Lần thứ hai, với quyền truy cập đầy đủ, xanh toàn bộ: format, clippy,
`cargo test --workspace --all-targets`, regressions tiền nhiệm P0 (8) / P1 (18) /
P2 (15) / P3 (15), discovery phase (22 tests), 18 required tests và documentation
checks, với source digest
`sha256:d78de82effebe4d06a5ab47f2619ea6592b81ff961228f0b0da9af85302d4a11`.

Digest đó khớp chính xác source tree P4 đã commit (digest chỉ loại
`docs/evidence/P4.*` và `docs/handoffs/P4.*`), nên integration gate P4 đã đạt tại
revision base. Tài liệu evidence P4 là stale, không phải code; P5 không được viết
lại evidence P4, chỉ ghi nhận phần xác minh mình đã chạy. Không có kết quả CI
remote nào được kiểm cho lần này, nên trạng thái workflow Ubuntu/Windows vẫn là
khoảng trống phải chuyển vào evidence P5.

P5 bảo toàn: schema revision và ID format P0/P1, single SQLite writer và host
fencing, journal và WorkingState là authority phục hồi, admission
frozen request/context P2, policy gate và receipt P3, và scoped memory P4 cùng
recheck revision trước dispatch.

## 2. Scope và kiến trúc được chọn

- Tạo `crates/harness-orchestrator/` làm owner của delegation contracts, task DAG,
  scheduler worker, worktree isolation, result integration và delegated crash
  recovery. Đây là logical owner `harness-orchestrator` đã được sổ tay triển khai
  nêu tên; không phải agent engine thứ hai.
- Mở rộng `harness-store-sqlite` bằng bảng delegation additive dưới schema
  revision riêng. Mọi write task, ownership, result, delivery và workspace đi qua
  transaction coordinator và host fence hiện có.
- Tái dùng runtime P2 làm worker engine: worker là preset của `RuntimeService` do
  host factory tạo, có session, inbox, cancellation token và context riêng. Không
  tạo runtime thứ hai.
- Mở rộng `harness-tools` bằng thao tác Git worktree do host sở hữu để shared Git
  metadata nằm trong một implementation.
- Mở rộng CLI bằng `ha run --agents N`, view task status/result/cancel/handoff và
  fixture demo multi-agent xác định.
- Mở rộng acceptance registry, phase verifier và CI matrix từ P0–P4 sang P5. Dừng
  trước P6.

Worker chạy trong cùng một writable host process. Daemon, remote worker,
marketplace, chạy nền sau khi CLI exit và sandbox isolation thật giữa các worker
in-process nằm ngoài scope. Worktree cô lập tranh chấp ghi đồng thời; nó không
phải security boundary và không artifact nào được claim khác.

## 3. Contracts cần chốt trước implementation

1. `TaskBrief` do host soạn và có version: objective, acceptance criteria, inputs,
   base snapshot, grants, budget, deadline, artifacts dự kiến và tham chiếu role
   preset. Role name không cấp quyền; mọi field authority là giá trị host explicit.
2. `AgentRole` là preset của cùng runtime. `AgentProfileId` ổn định qua các lần
   activation, `AgentRunId` là một activation, và ownership generation fence run
   đã chết.
3. Task lifecycle là `pending -> ready -> assigned -> running -> completed |
   failed | canceled`, với `blocked` tới được từ mọi live state. Dependency tạo
   thành DAG: cycle, self-dependency, dependency ID không tồn tại, task ID trùng và
   owner mơ hồ bị từ chối trước admission.
4. Worker report không phải host-accepted completion. `DelegatedResult` chứa
   outcome, summary, artifact references, base và result revisions, các revision đã
   kiểm và check receipts. Response rỗng, hoặc chữ "done" thiếu artifacts/receipts
   đã khai, không được settle accepted work.
5. Result gắn với một revision: branch revision của từng worker không phải evidence
   của integrated revision, và integration phải chạy lại final checks.
6. Budget bao gồm worker đồng thời, delegation depth, model requests và cost tính
   được. Usage thiếu không tính là zero, và hết budget là terminal cho dispatch mới
   thay vì mở rộng vô hạn.
7. Delivery đúng một lần *về logic*: child result, task transition và parent
   delivery commit trong một transaction; notification chỉ đánh thức reader.
   Consumption idempotent theo message ID ổn định, và parent session chưa chạy nhận
   inbox data mà không append tùy ý vào event log của nó.
8. Editing delegation cần repo input sạch đã xác minh. Input dirty bị từ chối kèm
   lý do rõ cho đến khi có snapshot path đã kiểm preservation; thay đổi user không
   bao giờ bị stash, reset hay xóa.
9. Parent cancel và parent pause là hai thao tác khác nhau: cancel lan xuống
   descendant, pause giữ durable state để resume.

## 4. Failure model

| Failure mode | Phòng vệ |
|---|---|
| Delegation vòng hoặc owner mơ hồ | Validate DAG trước admission; test cycle/dangling/self/duplicate. |
| Việc đã xong bị giao lại sau restart | Durable task state là authority; recovery không giao lại task `completed` hay child đã xong của run đã chết. |
| Mất parent notification | Result + delivery + task transition trong một transaction; replay giao đúng một lần logic kèm tham chiếu result gốc. |
| Consume delivery trùng | Message ID ổn định với cờ consumed được kiểm trong chính transaction ghi. |
| Parent chờ và bỏ đói children | Chờ thì nhả compute permit; test fairness với slots ít hơn số child. |
| Worker ghi đè nhau hoặc vượt scope | Worktree do host quản lý từ một snapshot đã xác minh, branch riêng từng worker, write scope đã khai, thay đổi ngoài scope bị chặn. |
| Shared Git metadata hỏng do chạy đồng thời | Một Git metadata lock tuần tự cộng integration worktree; test tạo worktree đồng thời. |
| Input dirty bị phá âm thầm | Yêu cầu input sạch, từ chối rõ ràng, không stash/reset, có assertion preservation. |
| Branch receipt bị nâng thành integrated evidence | Integration recheck fingerprint và chạy lại final checks trên integrated revision. |
| Child result giả scope hoặc vượt grant | Principal do host tạo; truy cập memory delegated recheck scope của child trước dispatch. |
| Side effect của child chưa rõ bị đánh dấu completed | Reconcile `outcome_unknown` tại coordinator; unknown không bao giờ thành accepted. |
| Vượt budget hoặc depth | Từ chối có type `budget_exhausted`/`depth_exceeded`; test depth cap và budget. |
| Shutdown mất descendant | Cancel/drain descendant, một shutdown completion dùng chung, store đóng cuối cùng. |
| Semantic memory bị dùng làm task authority | Completion chỉ đến từ durable task state. |

## 6. Test, RED/GREEN và gate

Acceptance target là `crates/harness-cli/tests/phase_p5.rs` cùng các module bổ
sung bên cạnh. Test dùng `SqliteStore` thật, session/runtime service thật, policy
gate và tool service thật, repository `git` thật trong temporary directory, và
binary `ha` đã biên dịch. Chỉ boundary thật sự bên ngoài được mock: model provider,
extractor/embedding boundary và clock. Transaction engine, authorization, DAG
store, worktree management và scheduler không bao giờ bị mock.

RED trước, GREEN theo từng lát cắt. Gate cuối:

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --all-targets --locked
cargo test -p harness-cli --test phase_p5 --locked
pwsh -NoProfile -File scripts/Verify-Phase.ps1 -Phase P5 -Json
pwsh -NoProfile -File scripts/Verify-Docs.ps1 -SelfTest
```

Discovery phải không rỗng và không ignore required case; regression tiền nhiệm
P0–P4 chạy bằng exact test name. Các lớp không chạy được trong môi trường này
(mutation tooling, coverage, advisory audit, CI đa OS) phải báo `skipped` hoặc
open, không suy từ local pass. Giới hạn `git clone` trên Windows ở mục 1 nghĩa là
full workspace suite cần quyền process/pipe đầy đủ; nếu lần chạy thiếu quyền đó,
failure phải được báo là giới hạn môi trường kèm cách tái hiện, không phải lỗi P5.

## 7. Setup, dependency và Git

Không dự kiến crate ngoài mới. Session của worker tái dùng dependency workspace đã
pin trong `Cargo.lock` (`tokio`, `tokio-util`, `sqlx`, `serde`, `serde_json`,
`thiserror`, `uuid`, `sha2`). Không cài tool hệ thống, credential, dịch vụ ngoài,
database ngoài hay API trả phí. Test worktree dùng `git` cài local qua tool layer
hiện có.

Thay đổi dự kiến nằm trong `crates/harness-orchestrator/`, phần additive của
`harness-store-sqlite`, `harness-runtime`, `harness-session`, `harness-tools`,
`harness-cli`, cùng `tests/acceptance/registry.json`, `scripts/Verify-Phase.ps1`,
CI phase matrix, test fixtures và SPEC/evidence/handoff song ngữ.

Assignment không yêu cầu publish. P5 không được commit, push hay publish, và phải
bảo toàn thay đổi user không liên quan cùng các contract đã được chấp nhận.

## 8. Exit và evidence

Tạo `docs/evidence/P5.en.md`, `P5.vi.md`, `docs/handoffs/P5.en.md` và `P5.vi.md`,
gắn với source digest cuối đã kiểm thử. Evidence map từng step/case sang exact
test, command, kết quả quan sát, fault window, toolchain và platform; ghi các lớp
skipped, known limitations, phần xác minh tiền nhiệm đã chạy, trạng thái
commit/push/CI thật và next safe action. P5 chỉ pass khi phase gate và regression
tiền nhiệm pass. Dừng trước P6.
