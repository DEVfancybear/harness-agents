## 2. Scope and chosen architecture

- Create `crates/harness-maintenance/` as the owner of backup manifests, restore
  validation, retention classes, tombstones and artifact garbage collection. It
  composes `harness-store-sqlite`, `harness-memory` and `harness-session`; it is
  not a second database authority and every write still goes through the
  existing transaction coordinator and host fence.
- Extend `harness-store-sqlite` with the additive tables retention needs:
  tombstones and a maintenance journal. Existing revisions are untouched.
- Extend the CLI with the `ha maintenance` command group — `doctor`, `backup`,
  `verify-backup`, `restore`, `retain`, `tombstones`, `gc`, `migrate-copy` and
  `release-matrix` — plus the `phase_p7.rs` acceptance target. The maintenance
  operations ship as subcommands of one group, and the operator guides document
  that shipped form rather than the `ha doctor` / `ha backup` spellings sketched
  in the runbook.
- Run every C01–C30 and K01–K14 case end to end with real stores and real
  processes, and record the result in the evidence.
- Package and smoke-test the CLI binary, and write bilingual operator docs.

In scope: consistent backup with artifact pins, restore into a **new** directory,
schema and artifact validation, migration from supported older fixtures,
interruption safety, explicit invalidate/archive/forget separation, tombstones
that block re-extraction, artifact GC over a grace period, the full acceptance
run, measurement, packaging and operator documentation.

Out of scope: production activation, a daemon, remote backup targets, a hosted
service, publishing artifacts to any registry, and P8 Web work. `invalidate` is
**not** `delete`: invalidation marks derived knowledge unusable while retaining
the historical record, and only `forget` removes content.

## 3. Contracts to fix before implementation

1. **Backup manifest.** A backup is a directory containing a SQLite snapshot
   plus a versioned manifest listing the source data directory, the schema
   revisions it contains, every referenced artifact with its content hash and
   byte length, the retention pins active at backup time, and a manifest digest.
   A missing artifact or a hash mismatch makes the backup invalid, and an invalid
   backup is never restored.
2. **Isolated restore.** Restore writes only into a destination that does not
   already hold an active store, validates the manifest digest, the schema
   revisions, every artifact hash and the tombstone set, and reports what it
   validated. Activation is a separate explicit maintenance action; restore alone
   never activates.
3. **Upgrade and downgrade.** Migrations run on a copy, never in place, and an
   interrupted migration leaves the source untouched. A store whose recorded
   schema revision is newer than the binary supports is refused for writes with a
   typed error while read-only inspection stays available.
4. **Retention classes.** `invalidate`, `archive` and `forget` are separate
   operations. `forget` requires an explicit target and a confirmation token,
   cascades to derived payloads, indexes and caches, writes a tombstone, and
   publishes which external or backup copies may still contain the data.
5. **Tombstones.** A tombstone records the forgotten source identity and reason.
   Re-extraction from a tombstoned source is refused, so deleted data cannot
   reappear through a later extraction pass.
6. **Garbage collection.** GC removes only artifacts that no durable record
   references, only after a grace period, and never while a backup pin or an
   unfinished job references them. A backup/GC race must not delete a pinned
   artifact.

## 4. Failure model

| Failure mode | Defense |
|---|---|
| Backup taken while work is in flight | The snapshot is taken inside the store's own transaction boundary; unfinished work is pinned, not dropped. |
| Backup misses an artifact | The manifest lists every referenced artifact with its hash; restore refuses an incomplete backup. |
| Restore over an active store | The destination is required to be fresh; an active data directory is refused. |
| Corrupted artifact bytes | Hash mismatch is reported per artifact and blocks activation. |
| Interrupted migration | Migration runs on a copy; the source stays readable and unchanged. |
| Older binary writing a newer store | Typed refusal for writes; read-only inspection still works. |
| Delete that silently reappears | Tombstone blocks re-extraction and the forget report names surviving copies. |
| GC deleting a pinned artifact | Pins and grace period are checked together inside the write transaction. |
| Benchmark claimed without measurement | Targets are reported as measured or unmeasured, never as achieved by assertion. |
| Missing live-provider credential | Recorded as unverified, with the scope decision left to the user. |

## 6. Tests and gate

The acceptance target is `crates/harness-cli/tests/phase_p7.rs` with modules
beside it. Tests use the real `SqliteStore`, real session/memory services, real
processes and real temporary data directories. Fixtures for deletion and restore
work only on disposable copies; an active store of the user is never touched.

Final gate:

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --all-targets --locked
cargo test -p harness-cli --test phase_p7 --locked
pwsh -NoProfile -File scripts/Verify-Phase.ps1 -Phase P7 -Json
pwsh -NoProfile -File scripts/Verify-Docs.ps1 -SelfTest
```

Every C/K case must be exercised with final executable evidence, not a summary.
Required tests must be discovered, non-empty and not ignored. Benchmark targets
stay targets until measured: an unmeasured number is reported as unmeasured.

## 7. Setup, dependencies and Git

No new external crate is expected. Backup uses the SQLite support already
available through `sqlx`, and everything else reuses workspace dependencies
pinned in `Cargo.lock`. No credential, paid service or external database is
introduced. Packaging uses `cargo build --release` for the current platform, and
producing artifacts for another platform is reported as not performed rather than
implied.

Expected changes stay inside `crates/harness-maintenance/`, additive changes to
`harness-store-sqlite`, `harness-memory`, `harness-session`, `harness-cli`, plus
the registry, phase verifier, CI matrix, fixtures, operator docs and the
bilingual SPEC/evidence/handoff.

The user explicitly requested commit and push for this assignment, so publishing
the source commit is authorized. No credential, runtime database, private
trajectory or built artifact may be committed.
