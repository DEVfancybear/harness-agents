## 2. Outcome and boundary

P3 introduces `harness-tools`, the sole owner of coding-tool policy,
approvals, rooted filesystem/search/patch operations, structured process
execution, Git inspection, task updates, project identity, and immutable
execution receipts. A P2 runtime response can be passed to a P3 coding-loop
adapter, but no model/tool call bypasses the same execution gate.

The CLI remains a composition and presentation layer. Its deterministic,
keyless fixture demonstrates an actual P2 provider response, P3 parsing,
approval, edit, verification process, durable receipt, restart recovery, and
pending-work view without a live credential. A live provider, host-wide sandbox,
network tool, plugin, browser, or multi-agent scheduler is outside this phase.

An action has four distinct forms:

1. proposed action — model/UI input, never authority;
2. validated execution intent — canonical action plus resolved workspace,
   fingerprints and policy decision, durable before the side effect;
3. immutable execution receipt — settled/unknown/denied fact that observers
   cannot mutate;
4. model/UI view — bounded, redacted projection of the immutable records.

Approval binds the actor, canonical invocation, resolved arguments, workspace
root and fingerprint, tool implementation revision, and policy revision. A
changed binding, expiry, consumption, cancellation, revocation, or stronger
ancestor denial invalidates it. A later allow can never override a parent or
ancestor denial.

## 3. Failure model and non-negotiable invariants

| Failure mode | Required defence and evidence |
|---|---|
| A model or CLI invokes a tool outside the gate | All public execution entrypoints call one `ToolExecutionService::execute` gate; direct adapters expose validation-only helpers, not side effects. |
| Policy transform changes arguments after approval | Validate identity/arguments, apply transformations, then revalidate and bind approval to the final canonical action/hash. |
| Approval replay, stale workspace, actor mismatch, cancellation or revocation | Single-use durable approval consumption is atomic with intent; before dispatch recheck cancellation/revocation and fingerprints. |
| Crash after intent but before/during/after a side effect | Commit intent before dispatch; settle atomically with receipt/event/artifact/projection; ambiguous outcomes remain `outcome_unknown` and reconciliation inspects rather than blindly reruns. |
| Observer/UI failure rewrites history | Receipt is immutable and persisted before observers; observer errors are independently recorded/presented only. |
| Workspace escape, symlink/junction traversal, secret leakage, binary/encoding ambiguity | Canonical rooted paths, no symlink/reparse traversal, protected/sensitive paths, `.gitignore` aware bounded walks, UTF-8/binary checks, hashes before/after and bounded redacted output. |
| Shell injection, hanging process, orphaned descendants, or false isolation claim | Structured executable/argv is the default; an explicit shell is separate. Bounded stdout/stderr, timeout/cancel, Windows Job Object and POSIX process-session cleanup are confirmed before reporting settled. Strict isolation is denied unless a real platform capability exists. |
| Git project identity or external edits are silently conflated | Register canonical root and Git common-dir identity; reassociation is explicit; fingerprints cover tracked/untracked state and stale receipts fail on changed inputs. |
| Storage error creates an unrecorded claimed success | Fault injection before tool-intent/settlement commits proves no success receipt or observer projection is emitted; reconciliation exposes pending/unknown work. |

## 5. Data, API, and safety decisions

1. P3 uses a separately named additive tools schema revision. It never changes
   P0/P1/P2 schema versions or reinterprets existing records. The SQLite writer
   atomically records a tool intent and single-use approval consumption before
   dispatch, and atomically records settlement, receipt, event, artifact scope,
   projection, and sequence marker after dispatch.
2. `ToolExecutionReceipt` remains the durable truth. It records canonical
   invocation/action hashes, policy/tool revisions, approval reference, before/
   after fingerprints, intent/outcome state and event sequence. Human/model
   views are redacted and bounded derivative records.
3. A workspace root is canonicalized at registration and every access. Relative
   paths only are accepted; parent escapes, absolute paths, symlinks/junctions,
   `.harness`, `.git`, credentials, private keys, and binary/unsupported text
   operations deny with stable typed errors. File listing/search respects
   `.gitignore`, has count/byte limits, and does not follow links.
4. Patches require exact expected content hash and UTF-8 source. Edits write a
   temporary sibling, flush, and atomically replace where supported; a mismatch
   means stale/unknown rather than silent overwrite. Before/after hashes and
   bounded diff metadata are persisted.
5. Process tools accept `executable + argv`; shell text requires an explicit
   shell action and approval. Output is drained while capped, timeouts and
   cancellation kill then wait for the platform tree mechanism. Windows uses a
   Job Object; POSIX uses a new process session/process group. These mechanisms
   are lifecycle cleanup, not filesystem/network isolation. `strict` isolation
   is a typed denial until a genuine sandbox backend is installed and verified.
6. Git project identity includes canonical root plus Git common-dir identity.
   A moved/changed identity requires an explicit reassociation. Git status/diff
   are read-only tools. `task_update` changes task projection only and never
   fabricates a process runner receipt.
7. Runtime integration is one directional: P2 normalizes and returns complete
   tool calls; P3 validates/executes them and stores results. Incomplete model
   arguments are denied before any tool intent is committed. No runtime crate
   depends back on P3.

## 6. Setup and dependency authorization

The existing Rust 1.97/Tokio/serde/sqlx stack is retained. This phase may add
the following exact workspace pins, recorded in `Cargo.lock`:

- `ignore = 0.4.25` (`Unlicense OR MIT`): established `.gitignore`-compatible
  walker for rooted, bounded list/search. Its 0.4.25 metadata was inspected
  locally; no process or external service is activated by it.
- `process-wrap = 10.0.0` (`Apache-2.0 OR MIT`, MSRV 1.87): safe Tokio wrapper
  that provides Windows Job Object and POSIX process-session/process-group
  child cleanup without adding unsafe code to this workspace. Its source and
  feature surface were inspected locally. Only `tokio1`, `job-object`,
  `process-session`, and `kill-on-drop` are enabled.
- The existing pinned `tokio = 1.53.1` gains its `process` feature for real
  subprocess tests and execution.

No credentials, privileged host service, external database, live model call,
or deployment is installed or activated. The acceptance target is
`crates/harness-cli/tests/phase_p3.rs`; P3 owns the new `harness-tools` crate,
additive types/store/session/runtime/provider wiring, CLI composition, phase
registry/gate, and bilingual evidence/handoff only.

The P3 gate must run formatting, clippy, workspace tests, exact P0/P1/P2
regressions, P3 discovery with no empty/ignored required tests, and docs
self-tests. Required behavior uses real SQLite, files, Git, and local

fixture. The final evidence must record one fresh post-edit gate, source digest
excluding only P3 evidence/handoff metadata, platform/tool versions, failure

live provider, and unrun platform verification if any).

`docs/handoffs/P3.en.md`, and `P3.vi.md`. The phase stops after P3 and does not
authorize P4 or runtime deployment.
