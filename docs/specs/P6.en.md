## 2. Scope and chosen architecture

- Create `crates/harness-extensions/` as the owner of the external plugin
  protocol: trust and capability contracts, the bounded stdio transport, the
  external tool bridge, the external model-provider bridge, the MCP client
  adapter, and skills/profile composition.
- External tools are exposed **only** through the existing P3 gate in
  `harness-tools`. The bridge adds a dispatch hook after the durable intent is
  committed; it does not add a second authorization path.
- `harness-kernel` keeps owning plugin graph, scoped registries, leases,
  generations and resource lifecycle. P6 registers extensions as kernel
  resources so unload/reload and ordered shutdown keep working.
- The MCP client uses the official `rmcp` SDK, pinned. MCP negotiation is the
  SDK's own contract and is never assumed compatible with this crate's custom
  plugin protocol.
- Extend the CLI with plugin/config inspection and an explicitly authorized local
  install/registration path, plus the `phase_p6` acceptance target.

In scope: local stdio extensions, local MCP fixture servers, versioned
filesystem skills, trusted profile composition, capability negotiation,
unload/reload with generations, and compatibility evidence.

Out of scope: marketplace, Wasm, arbitrary native dynamic loading, remote MCP
endpoints beyond a documented trust/network policy, external loop or storage
plugins, post-freeze context injection, and any implicit package download.

## 3. Contracts to fix before implementation

1. **Identity.** A plugin declares `plugin_id`, `implementation_version`, a
   build/content digest, provided and required `ServiceContract` versions, a
   config schema version, requested capabilities, a restart policy and whether
   its absence blocks recovery. Implementation SemVer, host protocol version and
   event schema version stay separate compatibility checks.
2. **Handshake before work.** A handshake carries the host protocol range, the
   plugin identity plus digest, advertised capabilities with versions, and the
   schema versions it implements. A digest mismatch, a protocol outside the
   supported range, an unsupported capability version or a requested host method
   outside the allowlist is refused before any input is admitted.
3. **Framing and limits.** Newline-delimited UTF-8 JSON only. A frame larger than
   the pinned limit is a protocol error, not an unbounded buffer. stdout carries
   protocol frames only; stderr is captured as bounded logs and never parsed as
   protocol. Response IDs must match an outstanding request exactly once;
   duplicate, unknown or malformed frames are protocol errors.
4. **Bounded concurrency and cancellation.** Inflight calls are capped. Cancel
   and EOF/exit are explicit: a call whose response never arrives has an
   **uncertain** outcome rather than a synthesized success, and the process tree
   is terminated when a deadline expires.
5. **Trust.** Reading a repository or profile file executes nothing. Loading an
   executable or resolving a secret requires an explicit user-level trust grant
   that pins the digest and an allowed capability set. Plugin processes run with
   a minimal environment: no secret-bearing inheritance, and no host credential
   is ever placed in a fixture environment.
6. **Authority.** The host assigns call IDs, principal, scopes, workspace roots
   and grants. A plugin-requested permission is a request, not authority, and it
   can never exceed the parent grant. Nested calls retain the parent invocation
   ID for correlation.
7. **Skills.** A skill has identity, version, digest and provenance, is discovered
   lazily, and its content is data: it cannot mint tool permissions. Skill text
   enters the context only through the P2 context builder, which alone admits and
   freezes blocks. A skill update becomes visible only at a recorded boundary.
8. **Unload/reload.** Unloading an extractor, tool or provider leaves jobs,
   cursors and session evidence intact. Reload creates a new generation; a late
   disposer from an older generation cannot remove the replacement. Remounting
   never authorizes repeating a side effect.

## 4. Pinned limits

The architecture documents deliberately do not fix frame or timeout numbers, so
P6 freezes them here and tests them.

| Bound | Value | Reason |
|---|---|---|
| `EXTENSION_PROTOCOL_VERSION` | 1 | Independently versioned from host API and event schema. |
| `MAX_FRAME_BYTES` | 1 MiB | Bounds one NDJSON frame; oversize is a protocol error. |
| `MAX_STDERR_BYTES` | 64 KiB | Bounded diagnostics per extension instance. |
| `MAX_INFLIGHT_CALLS` | 4 | Bounds concurrent calls to one extension. |
| `HANDSHAKE_TIMEOUT_MS` | 5 000 | A silent or slow handshake fails closed. |
| `DEFAULT_CALL_TIMEOUT_MS` | 30 000 | Default deadline before process-tree termination. |
| `MAX_SKILL_BYTES` | 256 KiB | Bounds one skill document read at admission. |

## 5. Failure model

| Failure mode | Defense |
|---|---|
| Malformed, oversize or non-UTF-8 frame | Typed `extension_protocol_error`; the call fails, the instance is unhealthy, no admission. |
| Duplicate or unknown response ID | Rejected; the matching pending call is not settled by a forged ID. |
| Output flood on stderr | Bounded capture; excess is dropped, never unbounded memory. |
| Ignored cancel | Deadline expires, the process tree is terminated, the outcome is uncertain. |
| Crash before a side effect | Call reports uncertain; a restart never auto-retries a mutating call. |
| Crash after a side effect | Durable intent remains; reconciliation is explicit, never a blind retry. |
| Plugin asks for an ungranted secret | Refused with a typed denial before the process starts. |
| Repository profile asks to load an executable | Refused without explicit user trust; reading config executes nothing. |
| Nested/MCP call tries to bypass policy | Same P3 gate; child call correlated to the parent invocation ID; grant intersected. |
| Arguments change after approval | Approval binding invalidates; execution denied. |
| Schema version change | Renegotiation required before use; an unsupported critical schema blocks resume. |
| Late disposer after reload | Registration undo is generation-bound and cannot remove the replacement. |
| Skill text tries to grant permission | Skill content is data; authority still comes from host grants. |

## 7. Tests and gate

The acceptance target is `crates/harness-cli/tests/phase_p6.rs` with modules
beside it. Tests use the real `SqliteStore`, the real P3 gate and receipts, the
real kernel registries and shutdown coordinator, and real extension **processes**
started from a compiled fixture binary. No in-process fake stands in for the
transport. External boundaries that are legitimately out of scope (a remote MCP
endpoint, a paid model API) are not exercised.

Final gate:

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --all-targets --locked
cargo test -p harness-cli --test phase_p6 --locked
pwsh -NoProfile -File scripts/Verify-Phase.ps1 -Phase P6 -Json
pwsh -NoProfile -File scripts/Verify-Docs.ps1 -SelfTest
```

Discovery must be non-empty and must not ignore required cases; predecessor
regressions P0–P5 run as exact named tests. Transport isolation is **not**
advertised as OS sandboxing: this phase provides a bounded protocol, a minimal
environment and an allowlisted method surface, not confinement of untrusted
native code.

## 8. Setup, dependencies and Git

One new external dependency is expected:

- `rmcp` (official Rust MCP SDK, Apache-2.0), pinned to an exact version with
  `default-features = false` and only the client and child-process transport
  features needed. No "latest" is written anywhere.

Everything else reuses workspace dependencies already pinned in `Cargo.lock`
(`tokio`, `tokio-util`, `serde`, `serde_json`, `thiserror`, `uuid`, `sha2`,
`process-wrap`). No system tool, credential, paid service or external database is
introduced. Fixture plugins are compiled in this repository and are run with a
minimal environment that contains no real secret.

Expected changes stay inside `crates/harness-extensions/`, additive changes to
`harness-tools`, `harness-providers`, `harness-kernel`, `harness-runtime`,
`harness-cli`, plus the registry, phase verifier, CI matrix, fixtures and the
bilingual SPEC/evidence/handoff.

The user explicitly requested commit and push for this assignment, so
publication is authorized. No credential, runtime database or private
trajectory may be committed.
