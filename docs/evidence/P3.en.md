## Delivered boundary

- `crates/harness-tools` is the sole P3 execution boundary. It owns versioned coding actions and provider schemas, policy transforms, explicit approvals, canonical workspace identity, rooted file/list/search/patch, structured process and explicit shell actions, Git inspection, scoped task updates, immutable receipts/views, and restart reconciliation.
- `harness-store-sqlite` adds an additive tools schema revision. Approval issuance/revocation/consumption, project registration/reassociation, tool intent, settlement, artifact scope, event/projection updates, sequence markers, and fault points are committed through the existing single writer.
- `harness-types`, `harness-session`, `harness-providers`, and `harness-runtime` add stable P3 IDs/errors, recovery folding for pending/unknown work, provider tool schemas and normalized tool calls, and a one-directional P2-to-P3 coding-loop adapter. Incomplete provider arguments stop before intent.
- `harness-cli` adds keyless `code capabilities --json` and a deterministic `code fixture` that runs a real P2 runtime response through P3 search, approved patch, verification, receipt persistence, and restart state inspection. No live credential is required.
- The acceptance registry, phase verifier, CI matrix, bilingual SPEC, and this evidence/handoff provide the phase boundary. P4 memory extraction, P5 scheduling/delegation, P6 plugins, P7 release/deployment, and P8 Web UI are not included.
