## 2. Ownership and contracts

[docs/specs/P5.en.md](../specs/P5.en.md) records scope, dependencies, the failure
model and the negative constraints.

`harness-orchestrator` is new and owns delegation contracts, the task DAG, worker
scheduling, worktree isolation, result integration and delegated recovery. Every
durable write goes through the existing P1 transaction coordinator and host
fence, so no second database authority exists. Delegation tables are additive
under their own schema revision `1`; the P1/P2/P3/P4 revisions are untouched.

Workers are presets of the existing P2 `RuntimeService`; no second agent engine
was introduced. `harness-kernel` supplies `ManagedResource` and
`ShutdownCoordinator`, so the scheduler participates in the existing ordered
shutdown. `harness-memory` remains the only memory owner; the orchestrator only
binds host-issued asset versions and re-validates them before dispatch.

New shared error codes were added to `harness_types::ErrorCode` for delegation
outcomes (`task_not_found`, `task_not_ready`, `task_dependency_failed`,
`task_ownership_conflict`, `dag_cycle`, `unknown_task_dependency`,
`duplicate_task_id`, `ambiguous_task_owner`, `delegation_depth_exceeded`,
`budget_exhausted`, `scope_authority_denied`, `dirty_workspace_denied`,
`integration_conflict`, `result_incomplete`, `scheduler_shutdown`,
`delivery_conflict`). These are additive; no existing code changed and no schema
document changed.

## 4. Fault windows and negative controls asserted

- `p5_c25...` arms `StoreFaultPoint::BeforeDelegationDeliveryCommit` and proves
  the task transition, result and parent message roll back together, then retries
  on a healthy store and delivers exactly once logically with the original
  result reference.
- `p5_c11...` commits a child result, stops the host before the parent consumes
  the notification, reopens read-only and confirms the completed task is still
  complete, is never reassigned, and the delivery is still durable.
- `p5_s03...` proves budget exhaustion is typed, depth beyond the cap is refused
  before a worker exists, requests are charged before dispatch so unreported
  usage is never zero, waiting on a child releases the compute slot, and a
  canceled worker reports an under-established outcome instead of success.
- `p5_s04_dirty...` proves a dirty input is refused with the exact reasons and
  that the user state is byte-for-byte unchanged afterwards: nothing was
  stashed, reset or discarded.
- `p5_s05...` proves an integrated revision is the only evidence, that a failing
  final check cannot produce a ready report, and that a changed user worktree
  refuses promotion of an earlier branch-level check.

## 6. RED history and confidence

RED was observed for real defects rather than only for missing APIs:

- `TaskPlan::compile` rejected honest plans because it treated the host
  coordinator as an in-graph parent; a fixture plan failed with
  `unknown_task_dependency` before the fix.
- `WorkspaceManager::inspect_input` deadlocked by re-acquiring the Git metadata
  lock through `fingerprint`; the CLI delegation run hung until the nested
  acquisition was removed.
- `next_settled` blocked forever once every worker had settled because the
  channel sender stayed alive; an outcome counter made stream exhaustion
  distinguishable from an empty stream.
- `live_worker_count` counted workers queued for a slot rather than running
  workers, so the documented slot bound appeared violated.
- `DelegationGrants::intersect` refused a legitimate equal-depth delegation.
- Integration fetched worker branches from the wrong remote, so every merge was
  reported as a conflict.
- Worker commits failed in the fixture repository because the worktree had no
  local Git identity, which made `result_revision` equal `base_revision`.
- Worktree creation re-derived a fresh project identity instead of using the
  verified repository registration, so two linked worktrees from one root could
  disagree about their project. `WorkspaceManager` now records a registration on
  the first verified inspection and resolves worktrees from it.
- The P0 registry test still assumed only P0-P4 were accepted, so it had to learn
  that P5 owns two continuity cases and seven steps.
- The phase verifier assumed every case is proven by its own acceptance target.
  It now supports target-qualified entries such as
  `phase_p5::strengthening::p5_c15_...`, so a later phase can strengthen an
  earlier case without weakening the gate.

Every fix was in implementation or fixture setup; no assertion was weakened and
no fixture expectation was edited to make an implementation pass.

Builder-authored tests: this is self-verification with limited independence.
Spec approval was not separately obtained, and no independent verification agent
was used, because the assignment forbids spawning agents.

- Changed-line and branch coverage: **unverified**, `cargo-llvm-cov` is not
  installed.
- Mutation testing: **not run**, no mutation tooling is installed.
- Advisory audit: **unverified**, `cargo-audit` is not installed. No external
  crate was added; `harness-orchestrator` depends only on workspace crates plus
  the already-pinned workspace dependencies.
- Secret scan: **unverified**, `gitleaks` is not installed. No credential is
  used or stored anywhere in P5.
- Remote CI on Ubuntu and Windows: **not verified**; this run is local only.
- True sandbox isolation between in-process workers: **out of scope** by
  contract. Worktrees isolate concurrent edits and are explicitly not a security
  boundary.
