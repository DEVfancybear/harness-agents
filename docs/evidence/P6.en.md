## 2. Ownership and contracts

[docs/specs/P6.en.md](../specs/P6.en.md) records scope, dependencies, the failure
model and the pinned limits; the runbook is
[docs/implementation/P6_EXTENSIONS.en.md](../implementation/P6_EXTENSIONS.en.md).

`crates/harness-extensions/` is new and owns the external plugin protocol:
contracts, transport, host, bridges, mcp and skills, plus two fixture binaries
compiled in that crate, `p6_fixture_plugin` and `p6_fixture_mcp_server`. External
tools remain reachable **only** through the existing P3 gate, so P6 adds a
transport and a dispatch hook, never a second authorization path.

Additive changes elsewhere:

- `harness-tools` gained `CodingToolAction::ExternalTool`, `ToolOutput::ExternalTool`
  and the `ExternalToolDispatcher` trait. The dispatch hook is placed after the
  durable intent commit.
- `harness-types` gained error codes (for example `extension_protocol_error`,
  `extension_protocol_unsupported`, `extension_digest_mismatch`,
  `extension_not_found`, `extension_untrusted`, `extension_capability_mismatch`)
  and two ID types used by the extension paths.
- `harness-cli` gained `ha extensions inspect|capabilities|register|skills`.
- `harness-kernel` keeps owning the plugin graph, scoped registries, leases,
  generations and resource lifecycle. Extensions register as kernel resources so
  unload/reload and ordered shutdown keep working.

P6-S01 and P6-S02 froze the limits the architecture documents left open:

| Bound | Value |
|---|---|
| `EXTENSION_PROTOCOL_VERSION` | 1 |
| `MAX_FRAME_BYTES` | 1 MiB |
| `MAX_STDERR_BYTES` | 64 KiB |
| `MAX_INFLIGHT_CALLS` | 4 |
| `HANDSHAKE_TIMEOUT_MS` | 5 000 |
| `DEFAULT_CALL_TIMEOUT_MS` | 30 000 |
| `MAX_SKILL_BYTES` | 256 KiB |

Host method allowlist: `host.echo`, `host.workspace.observe`, `host.task.read` and
`host.memory.search`. Environment allowlist: PATH, PATHEXT, SYSTEMROOT/SystemRoot,
TEMP, TMP, HOME, LANG.

One new external dependency was added: `rmcp`, the official Rust MCP SDK, pinned
exactly to `=3.4.0`, Apache-2.0, with the features `client`, `server`, `macros`,
`schemars`, `transport-child-process` and `transport-io`. `schemars` is already a
workspace-pinned dependency.

## 4. Fault windows and negative controls asserted

- `p6_k12...` drives a real fixture process through malformed input: a malformed
  handshake frame never yields a negotiated session, an oversize frame is refused
  rather than buffered (and `encode_line` returns `FrameLimitExceeded` at encode
  time too), an unsupported protocol revision and a capability the manifest never
  promised fail closed, a host method outside the allowlist returns
  `HostMethodDenied`, and a plugin that exits before the handshake is reported
  instead of retried.
- `p6_k12...` also proves the routing and liveness bounds: duplicate response IDs
  settle nothing (the first answer wins and no call is settled twice), an ignored
  cancel lets the deadline expire, terminates the process tree and reports
  `CallOutcome::Uncertain` naming the deadline instead of a synthesized success,
  and a stderr flood stays bounded by `MAX_STDERR_BYTES` and is never parsed as
  protocol.
- `p6_k13...` proves authority can only narrow: a nested request for an extra
  secret is refused `SecretNotGranted`, an extra capability is refused
  `ExtensionCapabilityMismatch`, a grant issued for another plugin is refused
  `ExtensionUntrusted`, a narrower grant is accepted, and the invocation
  (`tool_invocation_...`) and execution (`tool_execution_...`) identities stay
  distinct so a nested call always names its parent invocation.
- `p6_k14...` proves opening an untrusted repository profile executes nothing and
  resolves no secret while reporting `requires_user_trust` and the requested
  secrets; without a grant the runtime reports `InactiveReason::NoTrustGrant`
  with zero live processes; an ungranted secret refuses with `SecretNotGranted`, a
  wrong digest with `DigestMismatch`, and an aliased plugin id is also inactive
  with `DigestMismatch`; the inventory keeps the inactive entries and their
  reasons; and the running fixture reports `secret_present: false`.
- `p6_extension_processes_receive_a_minimal_environment` inspects the environment
  a real plugin process actually received: every name is in
  `ENVIRONMENT_ALLOWLIST` or was an explicit host override, no secret-bearing name
  is present, and a manifest that requests a non-allowlisted name is refused with
  `EnvironmentDenied` before any process is started.
- `p6_s06...` covers the lifecycle fault windows: a refused handshake leaves
  `HandshakeRejected` with no live process, an absent executable is
  `ExtensionNotFound` (K01), a failed activation leaves nothing running (K03), a
  stale registration token cannot undo the replacement generation (K05), a plugin
  that crashes after an effect is either answered or explicitly uncertain and
  never authorizes a blind retry (K11), and provider stream normalization rejects
  unknown event kinds and empty payloads with `ProviderProtocol`.
- `p6_s06_unload...` proves unload removes the process, its registrations and its
  inventory entry, and that reload produces a strictly newer generation with a new
  instance identity while the plugin identity and scope stay stable, so a late
  disposer from the older generation cannot remove the replacement. Unloading a
  plugin that is not loaded is reported, not silently ignored.
- `p6_s03...` runs the same durable gate: an `ExternalTool` action is prepared and
  then denied without an approval, with a `Denied` intent and outcome recorded as
  durable evidence; the same prepared call with an approval returns
  `ToolOutput::ExternalTool`; a nested external call keeps the parent invocation
  id and is still denied without its own approval; and once the extension is
  unloaded the same call records `OutcomeUnknown` instead of a silent success.

## 6. RED history and confidence

RED was observed for real defects rather than only for missing APIs:

- The fixture plugin reported a hard-coded digest that did not match the
  executable, so every handshake failed until the digest was computed from the
  running binary.
- `ExtensionRuntime` discarded the extension definition on unload, so `reload`
  silently returned nothing.
- Generation numbers were derived only from the live slot, so a reload after an
  unload reused generation 1 and tripped the monotonicity guard.
- `ServerConfig` and `InitializeResult` in `rmcp` 3.4.0 are non-exhaustive, so the
  fixture MCP server had to be built through the official builder API instead of a
  struct literal.
- Integration error mapping was too coarse: a plugin-id mismatch was reported as a
  digest mismatch, which hid the real cause until the reasons were separated in
  the fixtures and assertions.
- The phase verifier and the P0 registry test had to learn that P6 owns three
  cases and seven steps.

Every fix was in implementation or fixture setup; no assertion was weakened and
no fixture expectation was edited to make an implementation pass.

Builder-authored tests: this is self-verification with limited independence. No
independent verification agent was used, because spawning agents was not assigned
for this work.

- Changed-line and branch coverage: **unverified**, `cargo-llvm-cov` is not
  installed.
- Mutation testing: **not run**, no mutation tooling is installed.
- Advisory audit: **not run**, `cargo-audit` is not installed. One external
  dependency was added (`rmcp =3.4.0`, Apache-2.0) and no advisory status is
  claimed for it.
- Broad secret scan: **not run**, `gitleaks` is not installed. No credential is
  used or stored anywhere in P6, and no real secret is placed in any fixture
  environment; the minimal-environment test asserts that no secret-bearing
  variable reaches a plugin process.
- Remote CI on ubuntu-latest and windows-latest: **verified**. Run
  `35123056461` concluded successfully for P6 and P0/P3/P4/P5 on both platforms.
- Transport isolation: this phase provides a bounded protocol plus a minimal
  environment and an allowlisted method surface, explicitly **not** OS sandboxing
  of untrusted native code.
- Out of scope by contract: remote MCP endpoints, marketplace, Wasm, arbitrary
  native dynamic loading, and external loop or storage plugins.

The first remote CI run for P6 failed on **both** platforms while the local gate
was green, which is exactly the class of gap a local-only result hides. Every
extension test panicked with `compiled fixture binary missing at
target/debug/p6_fixture_plugin`.

Root cause: the two fixture executables lived in `harness-extensions`, but
`CARGO_BIN_EXE_*` is only exported to targets of the same crate, and the phase
gate runs `cargo test -p harness-cli --test phase_p6`, which builds only
`harness-cli` targets. The binaries existed locally only because a full
`cargo test --workspace --all-targets` run had created them.

Fix at commit `3efb061`: both executables moved into `harness-cli/src/bin` so
they are real targets of the crate that owns the acceptance test, and the test
support resolves them through `CARGO_BIN_EXE_*`. The `harness-extensions` library
keeps the protocol API and the integrations; only the executables moved. The fix
was verified by deleting both binaries and re-running the gate's exact discovery
command, which rebuilt them, and then by the green CI run above.
